## 1. 最善手・理論最強の定義

### 1.1 現実に目指すもの

相手の秘密の手札や未来の出目を知った後の最善手と、いま知り得る情報で勝率を最大にする手は違う。後者を目標にする。最善の判断でも悪い出目で負けることはある。

プレイヤーiが知る履歴を `h_i`、自分の方策を `π_i`、相手方策を `π_-i`、勝利報酬を `u_i` とする。固定された相手モデルに対する理想は、現在の1手だけでなく、その後の自分の方策も最適化した

`π_i* ∈ argmax_π_i E[u_i | h_i, π_i, π_-i]`

である。相手モデルが不確かなときは、そのモデルの分布についても平均する。常に同じ手を選ぶとは限らず、相手に利用されないために確率的に手を選ぶ方策も認める。

3〜4人のカタンには、未知のあらゆる相手に一律で最も勝てる唯一の戦略があるとは限らない。最大化の対象を決めずに「最強」は定義できない。

| モード | 最適化対象 | 保証の範囲 |
|---|---|---|
| 固定相手への最適応答 | 指定した相手方策に対する勝率 | 相手モデルが正しい場合に限る |
| 母集団に強い方策（製品の既定） | 固定した多様な相手母集団への平均勝率 | 測定した母集団・条件 |
| 頑健な方策 | 相手モデル集合での下側の成績、最悪ケース | 集合と目的関数次第。全員が協調妨害する想定は過剰に保守的になり得る |
| 均衡研究 | 単独の方策変更による改善余地の縮小 | 均衡でも未知の弱い相手を最も上手く利用するとは限らない |
| 縮小ゲームの厳密解 | 有限に定義した小ゲーム全体 | その小ゲームのみ。本番カタンへ保証を移せない |

勝者を1、他を0とする終了ゲームは定和として扱えるが、3〜4人なので二人零和ゲームの解法保証がそのまま使えるわけではない。CFR/ReBeLの二人零和での保証を、そのまま「カタンも収束する」と記述しない。[CFR論文](https://papers.nips.cc/paper_files/paper/2007/hash/08d98638c6fcd194a4b1e6992063e944-Abstract.html)、[ReBeL論文](https://proceedings.neurips.cc/paper/2020/hash/c61f571dbd2fb949d3fe5ae1608dd48b-Abstract.html)

### 1.2 いつなら「証明した最善手」と言えるか

固定相手モデル・正確な事後分布・有限のゲーム木に対し、情報集合の制約を守り、全合法手と偶然の結果を扱い、最適値を厳密計算または保証付き上下界で挟めた場合。選択手の下界が他手の上界以上なら、そのモデル内で最善と証明できる。

有限の縮小ゲームでは `epsilon` 最適性も検証する。本番では探索打ち切り、候補削減、学習した評価関数、近似した相手モデルがあるため、通常はこの保証を出せない。「探索した中で最高評価」と「真の最適」を区別する。

カタンには膠着や交易の循環があり、手番数を有限と仮定してはいけない。厳密解の対象は地平線と打ち切り報酬を明記した縮小ルールに限定する。無制限本番の収束や必ず終了する性質は別途証明が必要。400手番の実験上限を、ルール上の引き分けと勝手に同一視しない。

## 3. 情報公開の契約を最初に固定する

### 3.1 ルールと観測のバージョン

`rules_version` と `observation_profile` を別々に管理する。情報公開が違う対局は同じ勝率表に混ぜない。「エンジンが持っている」「JSONに入っている」は、人間に許された情報であることの根拠にしない。

M0で、実際に人間へ表示・通知される情報を棚卸しする。既存UIを維持する移行中は `legacy_app` として固定する。新しい「人間と同じ目線」プロファイルは次表を基準に人間UIと同時に導入する。CPUだけ新情報を受け取る移行は禁止。

| 情報 | 推奨契約 |
|---|---|
| 盤面、公開点、資源手札の総枚数、使用済み騎士、発展カード総枚数 | 公開 |
| 自分の資源、発展カード種類、今手番に買った自分の札 | 本人だけ |
| 相手の発展購入の時刻・枚数、公開された使用種類 | 公開。ただし内部のカードIDは非公開 |
| サイコロ、産出、建設コスト、成立した交易 | 人間に見える内容を公開 |
| 提案・対案・承諾・拒否 | 実際に相手へ表示された内容だけ。未送信の編集途中や取り消したローカル草稿は送らない |
| 盗みの資源種類 | 奪った本人と奪われた本人だけ。第三者には総枚数変化だけ |
| 相手の廃棄の内訳 | 人間に非公開ならCPUにも非公開。枚数だけ |
| 銀行の資源別残数 | 公開すると決めたプロファイルだけ正確値。通常はunknownを許す |
| 山の発展カード種類、実RNG、出目seed、他席の観測履歴 | 非公開 |
| 非公開カードの正解 | 終局後の評価器・学習ラベルのみ。対局中の入力や説明文には入れない |

**銀行は重要:** 内訳が公開なら、廃棄前後の銀行差分から廃棄種類が推測できる。「廃棄は秘密だが銀行の正確な内訳は常時公開」を、完全に秘密の廃棄と呼んではいけない。非公開プロファイルでは銀行も潜在変数に入れ、`19−実銀行−自分の札` を推定へ使わない。自分に提示された合法な銀行交換一覧から在庫の有無を推測するのは、自分も見られる範囲で許す。

### 3.2 境界

本番Engineだけが完全状態と実RNGを持つ。Observerが必要最小限を投影し、Agentは投影済みデータしか受け取らない。シミュレータは公開状態＋推定サンプル＋推論用RNGから新規構築する。

```text
Authoritative Engine (真のGame / RNG)
    -> Observer(viewer) -> ObservedEvent + Observation -> Agent
Agent: History -> Belief -> OpponentModel -> Search -> ActionDistribution
Search -> Simulator(公開状態 + BeliefSample + 推論RNG)
Action -> Authoritative Engine (最終合法性検査)
Evaluator: 真の状態は採点・終局後ラベルにのみ使用
```

新エージェントに本番 `&Game`、本番をcloneする関数、全席の履歴、秘密入り `ActionRecord` を渡さない。Observerとエージェントのモジュール境界を分離し、必要ならプロセスも分ける。オンラインで秘密を守る場合は、種と全行動の再配信をやめ、席ごとの観測を配るサーバ権威方式へ段階移行する。ローカルでCPUが秘密を使わないことと、悪意あるクライアントが秘密を解析できないことは別の要件。

## 4. 観測・履歴API

以下は概念APIであり、そのままコンパイルする完成コードではない。

```rust
struct Observation {
    viewer: PlayerId,
    rules_version: RulesVersion,
    profile: ObservationProfile,
    event_seq: u64,
    public: PublicState,
    own: OwnPrivateState,
    legal: Vec<Action>, // その席に実際に提示できる合法手のみ
}
struct ObservedEvent {
    seq: u64,
    actor: PlayerId,
    phase: Phase,
    turn_index: u32,
    payload: VisibleEvent,
}
trait Agent {
    fn reset(&mut self, public_config: &MatchConfig, inference_seed: u64);
    fn observe(&mut self, event: &ObservedEvent);
    fn decide(&mut self, obs: &Observation, budget: &Budget) -> Decision;
}
struct Decision {
    probabilities: Vec<(Action, f32)>,
    selected: Action,
    evidence: DecisionEvidence,
}
```

必要なイベントは、発展購入、公開使用、手番開始・終了、ロール、各産出、建設、交易の提案/回答/成立、廃棄、盗み、特別賞移転、終局。公開フィールドと本人だけの追加フィールドを明示する。第三者の廃棄/盗みへ、空欄の代わりに本物の内訳を埋めて後で隠す設計を避ける。

- `observe()`は自分の思考時だけでなく、他人の手番中も届く。
- 順序番号で重複適用を防ぐ。切断再接続は観測スナップショット＋不足イベントで復元する。
- 履歴圧縮は公開履歴の十分統計を目指す。ただし情報を落とす近似は明記する。
- 自分の合法手一覧も情報を含むため、同じ観測に含め、推定と非干渉テストに使う。
- CPUの推論seedは本番の出目等から導出しない。計測時の乱数ストリームも役割別に分ける。

## 5. 手札の推定（Belief）

### 5.1 状態

真の手札ではなく、あり得る隠れ状態の同時分布を持つ。

`b_t(z, θ) = P(隠れ状態z, 相手傾向θ | 自分の観測履歴h_i)`

zには相手全員の資源・発展札・購入世代・山の内訳、必要なプロファイルでは銀行も含める。各プレイヤーを独立に推定して、勝利点札の合計が5を超えるようなモデルは禁止。資源は各19枚、発展は騎士14・街道2・収穫2・独占2・VP5を共同で保存する。

初版は重み付き粒子フィルタを実装する。初期候補数は256、512、1024などを計測で選び、ブラウザ推論は小さい構成も許す。数値は設計上の出発点であり、性能保証ではない。履歴が強く制約した小状態では正確な列挙と比較する。

各粒子はルール上可能な状態だけを持つ。銀行残数、枚数、買った当日の使用禁止、公開済みカードとの整合を検証する。粒子の有効数 `ESS=1/sum(w^2)` を測り、例えば粒子数の半分未満なら再サンプルと制約付き再活性化を行う。

### 5.2 更新

一般形:

`b_(t+1)(z',θ) ∝ P(o_(t+1)|z',a_t) × Σ_z T(z'|z,a_t) P(a_t|I_actor(z),θ) b_t(z,θ)`

ルールによる観測整合と、相手の行動選択の尤度を分ける。相手の情報集合 `I_actor` はその相手が知れるもののみ。観測された相手の行動を扱う場合と、CPU自身が選んだ介入を扱う場合を区別し、自分の行動を相手の秘密の追加証拠として二重に利用しない。

| イベント | 更新 |
|---|---|
| 資源産出、建設、公開交易 | 見えた増減を適用し、払えない粒子を除く |
| 第三者の盗み | 盗まれた側の粒子内の資源比に従って移動。実際の種類は参照しない |
| 自分が当事者の盗み | 自分に知らされた種類で条件付けする |
| 非公開の廃棄 | 合計枚数を満たす廃棄を相手方策から生成。実廃棄内訳は使わない |
| 発展購入 | 粒子内の山から引き、購入世代に追加。本人の購入なら私的観測種類で条件付け |
| 発展使用 | 指定種類を持ち、当日購入以外から使える粒子に限定 |
| 提案・承諾 | このアプリの支払い可能性が検査される条件なら資源下限の証拠に使う |
| 拒否 | 「その資源を持っていない」と確定しない。利益・脅威・性格による拒否もある |
| 勝利せず進んだ | その時点でルール上自動勝利判定が行われた場合だけ、不可能な隠れVPを除外 |

粒子が全滅したら本番の手札で埋めない。観測履歴から制約を再構築し、行動モデルのソフト尤度を緩めて再生成する。ルールのハード制約は緩めない。なお復元できなければ診断を残し、観測だけで動く保守的な合法手方策へフォールバックする。

## 6. 発展カードの勝利点予測 — 優先して実装

### 6.1 事前分布

まだ使われていないカードを勝利点と決めつけない。観測が種類・枚数以外にない交換可能な初期モデルなら、未知札N枚にVPがK枚あり相手がm枚持つとき、

`P(VP枚数=k) = C(K,k) C(N-K,m-k) / C(N,m)`

を基準にできる。ただし、過去に「持っていたのに使わなかった」選択が観測された後も、この超幾何分布だけに戻してはいけない。それが現在の推定の主な不足である。

### 6.2 保持期間より、使用機会

長く保持された札がVPらしいという推測は妥当な手掛かりだが、騎士を盗賊対策で温存する、独占の機会を待つ、街道の有効な置き先がない、初心者がカードを忘れている場合もある。長さだけで単調に確信度を上げない。

観測する特徴:

- 購入から経過した**その人自身の手番数**。実時間や他人の手数ではない。
- 購入した手番で使えない制約。別の発展を使用済みの手番では、さらに使わないことを証拠にしない。
- 盗賊が本人の高産出地を塞いでいた、騎士で最大騎士力を取れた可能性。
- 街道の残駒・合法な延伸先・開拓余地。
- 収穫で有力な建設が可能になる見込み、独占対象の資源の推定量。
- 公開点、勝利までの距離、新しい発展購入、公開使用、相手モデル。
- 各手札仮説における「使えたか」と「使う価値」。評価器が本物の相手手札を覗いて判定してはいけない。

公式の説明でも、長く未使用で保持されたカードから勝利点を推測する考え方が紹介されている。一方で通常の発展札は買った手番には使用できず、VPによる勝利は例外である。[日本カタン協会の説明](https://catan.jp/guide/glossary/development_cards/)、[公式基本ルール](https://www.catan.com/sites/default/files/2021-07/catan-25th-rules_eng-200313.pdf)

### 6.3 購入世代を追うが、カードIDを追わない

内部の実カードIDや、他人がどの購入回のカードを使ったかを渡してはいけない。公開された購入イベントごとの世代（cohort）を作り、「どの世代から使われたか」も潜在変数にする。

例: 3巡前に1枚、前巡に1枚買い、今騎士を使用した場合、古い札が消えたと断定しない。どちらの世代から騎士が使われたかを、それぞれ合法な仮説として重み付けする。実装がカード種類ごとの個数だけで実IDを持たなくても、推定側でこの購入履歴を保持できる。

### 6.4 不使用の尤度

初版の説明可能なモデルとして、札の種類c・局面特徴x・相手傾向θに対する使用機会ごとの使用確率 `q(c,x,θ)` を持つ。

単一カードを未使用で終えた例では:

`P(c | 不使用履歴) ∝ P(c) × Π_t (1-q(c,x_t,θ))`

VPは通常使用しないため、その生存尤度が高い。だが実装は複数カード・1手番1枚制限・世代の不確定性を含む手札単位の行動モデルにする。独立なカードごとの不使用を単純に掛けると、複数枚持つ相手を過剰にVPと推定してしまう。

説明用の仮定: 事前VP確率20%、非VPは使用機会ごとに50%使うと仮定し、3機会使わなければ `0.2/(0.2+0.8×0.5^3)=約66.7%`。これは説明用の架空の数値であり、実装の固定ルールにも実測値にも使わない。

不使用は原則として「使用可能な自分の手番を終えた」単位で観測する。クリックごとに同じ証拠を掛けて確信度を水増ししない。全行動系列の尤度を使う版へ移行するなら、手番終了時の不使用尤度を別途掛けず、二重計上を避ける。

### 6.5 推定の出力と判断への接続

プレイヤーpごとに以下を出す:

```text
P(hidden_vp = 0..5)
E[hidden_vp]
P(actual_vp >= 8), P(actual_vp >= 9)
P(pが次の自分の手番終了までに勝つ | 候補行動)
P(pが自分iの次手番までに勝つ | 候補行動)
calibration_version / confidence_diagnostics
```

公開点7＋推定VP平均1という平均値だけに潰さない。「ほぼ1点」なのか「0点か2点が半々」なのかで、即勝利のリスクは違う。粒子ごとの勝利条件、交易成立後の建設、騎士力・最長路の移転まで通してリスクを推定する。

`threats()`の公開点依存を段階的に置き換える。単に `公開点 + E[VP]` へ差し替える版は比較用に残すが、最終候補は勝利ハザードを評価する。相手を妨害すること自体ではなく、自分の勝率がどう変わるかで交易拒否・盗賊対象・競合する建設を選ぶ。

「8点なら全交易拒否」の固定規則は入れない。自分がその交易で先に勝てる場合や、別の相手の即勝利を止める場合を取り逃がすため。

### 6.6 勝利点推定の必須テスト

1. 追加の行動情報がない小例で、超幾何分布と粒子分布が許容誤差内で一致する。
2. 非VPなら使う確率を高くした合成相手では、複数の有効機会の不使用でVP確率が上がる。
3. 買った当日、別カード使用済み、置ける道がない局面では、対応する不使用だけで不当にVP確率が増えない。
4. 温存型・無作為型・初心者型では過信を抑える。全状況で時間とともに必ず増えるテストは書かない。
5. 複数購入後の使用で、公開されていないカード世代を決め打ちしない。
6. VP合計≤5、発展全体25枚、種類別保存を各粒子で満たす。
7. 勝利判定が行われたのに終局しなかったという証拠は、正しいタイミングだけで使う。他人の番で10点相当になっても直ちに除外しない。
8. 同じ観測履歴で実カードだけを差し替えても、予測・行動分布・説明が変わらない。
9. 未使用対局でBrier score、log loss、信頼度図を測る。勝率だけで推定の正しさを判定しない。
10. 終局前に正解ラベルをエージェントへ返さず、採点器だけが真のVP数と比較する。

## 7. 相手モデル

隠れ手札と相手の傾向を別々に決め打ちしない。`P(z,θ|h)`として、カードを持っていないのか、持っていて温存しているのかの両方を維持する。

初版のθは、早めに使う型・温存型・建設重視・騎士重視・無作為/初心者型などの方策混合とする。これはゲーム内で相手の性格を断定して表示するためではなく、予測の過信を抑えるため。相手のCPU難易度や内部重みをエンジンから読み取らない。

行動尤度は観測から更新する。非常に小さな尤度に床を設けてモデル外の行動で全滅しないようにするが、違法手のような不可能性は床で救済しない。温存の推定モデルと探索で用いる相手方策に矛盾を作らない。

モデルをオンライン更新する期間と、評価時に固定する条件を明記する。相手の学習履歴を別対局から無断共有しない。まず1対局内での適応とし、長期個人モデルは別機能として扱う。

## 8. 探索: 自分の手番だけから情報集合を使う複数手番探索へ

### 8.1 二段階

近い戦術には、小さな正確探索を使う。銀行交換→建設、道路→開拓、騎士力獲得、即勝利、7での廃棄など。長期判断には情報集合を扱うMCTS系探索＋勝率評価を実装する。最初は学習なしのロールアウト方策で動作させる。

ISMCTSは情報集合を木の単位とする参考になるが、そのまま採用して最適性が保証されるとはしない。[ISMCTS論文](https://eprints.whiterose.ac.uk/id/eprint/75048/1/CowlingPowleyWhitehouse2012.pdf)

### 8.2 最も避けるべき失敗: 推定を真実だと思って未来を読む

推定サンプルが「P1に羊あり」となっても、盤上でそれを知る機会がなければ、将来の自分がその真相を見て行動を変えてはいけない。同じ情報集合の方策をサンプル間で共有する。完全情報で解いた各サンプルの最善値を平均するだけでは、実際には選べない都合の良い方策を評価することがある（strategy fusion）。

さらに、シミュレーション中の相手にルートの自分だけが知る情報を渡してはいけない。相手も自分の秘密の札と公開履歴に基づいて動く。

- ノードキーは、行為者とその席の観測履歴/十分統計。真の隠れ状態や他席の私的履歴をキーへ入れない。
- 行為者の私的観測は、サンプル内でその席に渡されたカード・盗み等から再構成する。
- 相手方策へ入力するのはその相手の情報集合。自分のルート事後分布で条件付けた秘密を、相手の信念だと思って渡さない。
- 公開ノードと私的信念を分離する案を設計する。単なる毎ノードの再サンプリングで整合が保たれるとは仮定しない。
- 初期実装で近似的なroot samplingを使うなら、近似箇所を明記し、後述の小ゲームで誤りを検出する。

### 8.3 木探索の要件

- 3〜4人それぞれの勝利確率ベクトルをバックアップする。相手全員を常に自分を妨害する一人の敵として扱う方式を既定にしない。
- 相手ノードは観測から推定した相手方策で分岐する。単純maxで選ぶ方式と混同しない。
- 手番内のアクション深さだけでなく、何回の相手手番・自分の次手番まで読んだかを計測する。
- 自分が将来受け取る観測で枝を分ける。まだ観測していない秘密で枝分けしない。
- サイコロは既知の確率。購入と盗みは信念に条件付けた確率でサンプル/列挙し、未来のseedを読む方式に戻さない。
- 終局判定は正しいプレイヤーの手番で行い、最長路の切断、最大騎士力移転、購入直後のVP勝利も含める。
- 深さ打ち切りは勝率評価器へ渡す。序盤の資源量の点数を、そのまま勝率と呼ばない。
- 各根候補へ最低探索数を割り当て、残りを不確実性・価値に応じて配る。同じサンプル集合を使うときも、行動順による打ち切りの偏りを避ける。
- 逐次的な探索停止は、単純な固定標本の区間を都合よく繰り返し覗く方式にしない。探索用の信頼度と、後述の採用検定を分ける。
- 木・信念の再利用は、実際に観測したイベントで更新し、別人の私的枝へ誤って移らない。

### 8.4 先に用意する小ゲーム

隠れ札2種類・少数枚・2〜3行動・有限2手番程度の合成環境を作る。

A: 同じ観測なのに隠れ状態ごとに都合よく別の手を選ぶ探索を検出する。
B: 相手には見えない自分のカードを、相手が知っているように応答する探索を検出する。
C: 確率的方策が必要な二人零和の小ゲームで、混合方策と既知の最適値を比較する。
D: 三人の利害が分かれる例で、相手全員を単一の敵とする評価との差を確認する。
E: 有限Catan縮小ルールで、指定相手モデルへの厳密な最適応答値と近似探索を比較する。

縮小ソルバは保証を検査する物差しであり、本番カタンを解いたという成果には数えない。

## 9. 全合法手に近づける行動生成

現在の代表形だけの交易生成を「ルールで可能なすべての手」と呼ばない。合法性と探索候補の優先順位を別レイヤーにする。

- 建設・発展・盗賊・廃棄は全合法手の生成器を持つ。廃棄の組合せも資源ごとの上限と指定総数から生成する。
- 交易のgiveは自分が払える束、wantはルールの有限な資源上限内の束とし、同資源を両側に置く禁止など既存ルールを守る。相手が実際に払えるかを、本物の手札で候補削除しない。
- 全交易の一括列挙は高価なので、建設不足を埋める束、余剰資源の放出、港比率を基に優先生成し、探索回数とともに候補を増やすprogressive wideningを使う。
- 時間無制限・計算量を増やす実験では、除外した候補が永遠に出ない構造を避ける。全候補へ非ゼロの提案確率を与える方式も比較する。
- OR対案は最大4本の候補集合として扱う。UIの「候補を積む」中間操作と交渉としての送信を区別する。v2の束アクションから既存Action列へ変換して合法性を再検査する。
- 複数銀行交換をマクロ化する場合、中間状態の在庫・可用資源・勝利判定などと等価であることを証明/テストする。マクロにより途中で選べた戦略を消さない。
- 拒否履歴は、同じ手札・盤面・交渉状況での重複を抑える。条件が変わった後まで永久禁止しない。自由な束を増やした際は既存の有限ビットマスクだけでは全提案を記憶できないことに注意する。
- 「もう提案しない」の終了行動を常に確保する。循環検出・探索内部の打ち切り・本番ルールを区別する。

## 10. 初期配置と戦術

初期配置も最初の1軒だけを静的な産出点で決めない。蛇行順の残りの配置、他者の配置予測、自分の2軒目、初期資源、港への接続、将来の拡張可能性を読む。相手がどこへ置くかは相手モデルの分布として扱う。

戦術の必須局面集:

- 一見損な銀行交換を挟むと即勝利になる。
- 都市化より道路→開拓を優先しないと土地を取られる。
- 騎士を使ってから建設すれば勝つ／次巡の盗賊対策として温存した方がよい。
- 相手の公開7点＋隠れVP分布により、同じ資源交換の危険度が変わる。
- 最長路を奪う、または相手の路を開拓地で分断する。
- 独占で得る資源を実手札ではなく信念から評価する。
- 7で捨てる束が、次の建設・港交換・勝利への道を保つ。
- 交易相手自身ではなく別プレイヤーの勝利が迫る局面。

各局面は正解の根拠を付ける。「旧CPUが選んだ手」を正解にしてはならない。

## 11. 学習による評価・方策

M1〜M4の正確性を満たした後に導入する。最初は既存評価器を葉評価とする比較版を維持する。

候補ネットワーク:

- 盤面のグラフ表現または小規模Transformer。
- プレイヤー順序・所有者、公開点、資源の事後分布、発展購入世代・未使用機会、私的な自分の手札、フェーズ、交易条件を入力。
- 方策ヘッド: 合法行動/束の生成分布。
- 価値ヘッド: 各プレイヤーの終局勝率、打ち切りを含めるなら未決着も別に扱う。
- 補助ヘッド: 隠れVPの分布、次の自己手番での勝利ハザード、相手の応答確率。

学習データも観測投影から作る。真の隠れVPは補助タスクの正解ラベルに使えるが入力に混ぜない。正解ラベルを付けるための全知ログと、エージェントが読める観測ログを別ファイル/スキーマにする。初版では全知criticを使わず、教師からの漏洩経路を小さくする。

対局単位でtrain/validation/testを分け、同一対局の別手番を別splitへ入れない。新しい盤seedだけでなく、学習に使っていない相手方策群にも評価する。過去世代、現行、構築型、交易型、温存型、無作為型を含むリーグを用いる。最新コピー同士だけで回して特定戦略へ崩れないようにする。

勝利を主報酬とする。VPや資源を補助報酬にした場合は、勝たずに稼ぐ報酬ハックと目的変化を測る。終局率の低下をVP増加で正当化しない。

二人不完全情報のReBeL等は設計の参考で、Catanへの収束保証ではない。多人数で強い実例としてPluribusがあるが、ポーカーでの成果からCatanの理論最強を主張しない。[著者公開のPluribus論文](https://noambrown.github.io/papers/19-Science-Superhuman.pdf)

## 12. 推定と探索の説明出力

各判断に、選択手・比較した上位手・推定勝率・計算量・推定の不確実性を保存する。ユーザー向けの説明は任意表示にし、UIをログで埋めない。

例: 「公開点は7点。未使用の発展札と使用機会から、次の手番で勝つ危険を高めに推定したため、この交易は見送った」。実際に計算した根拠だけを書く。

秘密の正解を説明へ出さない。『相手はVPを2枚持っている』ではなく、校正済みの分布や『可能性がある』で示す。研究用ログでも、推定と正解を別欄にし、対局中にAgentから正解欄へアクセスできないようにする。

## 13. 計算予算・製品運用

初期の目標値（実測で調整）:

| プロファイル | 思考時間の目標 | 用途 |
|---|---:|---|
| fast | 50〜150ms程度 | 軽い端末・通常操作 |
| strong | 300〜1000ms程度 | ローカル最高難易度 |
| analysis | 5〜30秒程度 | オフライン局面研究・強化の上限探索 |

思考はWeb Workerへ移し、UIの描画・キャンセルを止めない。サーバは部屋ごとの時間/メモリ制限を持ち、複数部屋で計測する。数字は約束するレイテンシではなく、ベンチマークで採否を決める予算。

予算切れ時には最後に完了した合法な行動分布を返す。実時間予算の比較だけでなく、固定シミュレーション数・固定推論seedの再現可能モードを用意する。GPUがないWASM用には小モデルや蒸留版を用意し、サーバ版と別々に勝率を測る。

モデル、観測、ルール、特徴量のバージョンを一致させ、不一致なら静かに誤動作せず互換な旧CPUへ戻す。

## 14. 検証・採用条件

### 14.1 公平性が最優先

同じ観測履歴を生む複数の完全状態に対し、同じ推論seedと固定予算で、予測・行動分布・説明が一致することを検証する。真の隠れカードだけを変えるだけでなく、本番RNG、他人の盗み結果、非公開廃棄、デッキ順序、内部カードID、ログの隠しフィールドも対象にする。

相手シミュレーションも同様に、その相手に見えない自分の秘密だけを変えて入力/方策が変わらないことを検証する。ルートの判断が公平でも、内部の相手モデルが全知なら不合格。

公開情報そのものが変わる状態対は非干渉テストに使わない。例えば同じ公開VPなのにゲーム終了フラグが変わる不正な比較を作らない。

### 14.2 推定の採点

保存則、合法性、正確列挙との一致を先に合格させる。次に未使用の相手でBrier/log loss、校正曲線、粒子全滅率、ESS、観測ごとの更新時間を測る。単にVP確率を高く出して当たった例を集めない。

「保持履歴なし」「保持期間だけ」「使用機会あり」「相手傾向もあり」をアブレーション比較し、推定の改善が勝率へつながるかを別に測る。

### 14.3 対戦評価

- ベースライン: 本書作成時の最高難易度を固定。途中で相手を更新しない。
- 3人は6順列、4人は24順列を使う。同じ盤/乱数ブロックを複数順列で使ったら、統計ではブロックとして扱う。
- 候補1対固定旧版3、同型戦、異なる戦略の混合リーグ、学習に未使用の相手、各難易度を分けて測る。
- 1回の小さい比較から採用しない。探索/調整用、候補選択用、凍結後の最終テストを分離する。
- 最終テストは事前に試合数・seedブロック・停止規則・合格条件を保存する。目安は約1万局からだが、必要数は検出したい改善幅と分散で決める。24や6の倍数にする。
- 必ず、生の勝利数/全試合数、未決着数、95%区間、平均手番、1判断のp50/p95/max、メモリ、条件を報告する。
- 打ち切りを分母から消して勝率を上げない。決着条件付き勝率は副指標にし、主指標は全対局を分母にした勝利率と未決着率。公式の引き分け扱いを追加するならルールを別バージョン化する。
- 共通乱数のpaired比較では対応を保ったブートストラップ等を使い、相関する試合を独立標本と仮定しない。行動が変わると消費する偶然も変わる点を明記する。
- 最終テストの結果を見てさらに重みを変えたら、そのセットはもう最終テストではない。新しい未使用セットを確保する。

採用ゲート: 公平性/ルール違反0、事前に決めた比較で勝率改善が支持される、重大な相手群での退行なし、停止率の悪化なし、予算内。満たさない変更は実験版として保存し製品へ自動昇格しない。

### 14.4 「最適性」の測定

本番Catanのexploitabilityを厳密計算したと宣言しない。有限小ゲームでの厳密最適応答との差、指定した攻撃的方策群への弱点、相手母集団での成績をそれぞれ別の指標として出す。近似best responseで発見した弱点は有用だが、弱点が見つからなかったことは弱点が存在しない証明ではない。

既存ファイルは温存し、新モジュールを追加する。名前は提案であり、まだ存在しない。

| M0 | 現行凍結、観測契約、seed/ルール台帳 | 人間とCPUの情報表が一致し、銀行・廃棄・草稿公開が明確。現行版の再現可能ベンチマーク |
| M1 | 席別イベント、履歴API、本人だけの私的情報 | リプレイ/再接続で同じ観測と予測を復元。秘密情報を改変しても入力不変 |
| M2 | 購入世代、資源/発展の制約付き推定、保持/使用機会モデル | 第6.6節と保存則テスト合格。未使用対局で校正結果を報告 |
| M3 | 隠れVP・勝利ハザードを戦術判断へ接続 | 公開7点＋潜在VPの局面集で根拠付き判断。対戦アブレーションで採否決定 |
| M4 | 情報集合探索、相手手番、候補拡張 | strategy fusion/相手の全知化を小ゲームで検出・解消。固定予算比較 |
| M5 | 多様なリーグ、観測入力の方策/価値学習 | train/test分離、未知相手へ評価、推定校正と勝率双方の記録 |
| M6 | 時間/メモリ最適化、WASM Worker、サーバ統合 | 3/4人・再接続・複数部屋・予算切れで合法動作、旧UI回帰なし |
| M7 | 凍結後の独立最終評価、採用/不採用 | 全試合ベースの勝率と区間、停止率、性能、限界を報告。公開サイト反映は別途明示 |

M0〜M3だけで完成した機能として渡せる。M4〜M5は研究工程であり、確実に勝率が上がるとも短期間で終わるとも約束しない。各段階の速度を実測してから、対局生成・学習の所要時間を見積もる。

## 17. 禁止する近道

- 真の相手手札、デッキ内訳、次の出目、実seedを推定や特徴量へ使う。
- 公開されていない相手の合法手一覧・カードID・内部難易度を読む。
- 長く持っている札を100%VPと決める。
- 各秘密サンプルで全知最適プレイして平均し、情報集合の制約を無視する。
- CFR、MCTS、自己対戦、ニューラルネットの名前だけで「理論最強」とする。
- 同型同士が25%だから強いと結論する。
- 途中経過だけで高勝率を宣伝する、未決着を隠す、遅い試合を無断で除く。
- 現在の合法手生成器にない手を、ルール上存在しないものとして扱う。
- 公平性の問題を強さと引き換えに残す、推定全滅時に秘密の正解へ戻る。

## 18. 引き継ぎ成果物

実装担当AIは、変更コードだけでなく次を提出すること。

1. 観測仕様と脅威モデル（CPUの公平性とオンラインの対不正性を区別）。
2. 動作する履歴/信念/相手/探索の各モジュールと、旧CPUとの切替。
3. 保持履歴によるVP推定のテストと校正図、真の値と推定値を分離した評価。
4. 再現コマンド、ルール/情報設定、seed、commitまたは作業ツリーハッシュ、モデルハッシュ。
5. 生の勝敗と未決着を含むCSV/JSONL、95%区間、アブレーション、計算コスト。
6. 未実装事項と保証しない範囲。全工程完了と各段階完了を区別する。

現行の開始用確認コマンド:

```powershell
Set-Location C:\catan_lab
git status --short
cargo test --workspace --profile bench-debug
cargo build --release -p catan-cli
.\target\release\catan.exe match max baseline baseline baseline --games 240 --seed 1700000 --no-time-limit
```

現時点のCLIの `baseline` は以前の2手読み・推定1通り版を指す。v2の対照には、本書作成時の `max`（推定3通り）を別名 `v2_control` 等で凍結して使用する。弱い旧方式だけを対照として改善を主張しない。

この240局は動作確認用であり、最終の強さの証明には使わない。本書作成時の最高難易度を固定した後、新版を別名で追加して比較する。
